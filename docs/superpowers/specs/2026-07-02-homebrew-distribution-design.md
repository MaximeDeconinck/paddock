# Homebrew distribution via cargo-dist design

Date: 2026-07-02
Status: approved (design)

## Problem

paddock has no distribution channel. The README's Install section only offers
`cargo install --path crates/paddock` (requires a Rust toolchain + a clone) and
a promise that "A Homebrew formula is coming". The competitor llmfit installs
with `brew install llmfit` (homebrew-core, prebuilt bottles) plus a
`curl | sh` script. Install friction blocks adoption, which is the stated goal.

## Goal

On every `git tag vX.Y.Z` pushed to the `paddock` repo, a GitHub Actions
pipeline builds the Apple Silicon binary, publishes a GitHub Release with the
artifacts, and pushes an updated Homebrew formula to a dedicated tap repo. End
users install with:

```
brew install maximedeconinck/tap/paddock
# or
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/MaximeDeconinck/paddock/releases/latest/download/paddock-installer.sh | sh
```

`brew upgrade` tracks new releases automatically.

## Decisions (locked)

- **Tool: cargo-dist** (the `dist` CLI by axodotdev). It generates the release
  CI, builds artifacts, cuts the GitHub Release, and pushes the Homebrew
  formula. The Rust-ecosystem reference for this.
- **Target: `aarch64-apple-darwin` only.** paddock is Apple Silicon focused;
  Intel/Linux deferred.
- **Installers: `homebrew` + `shell`.** Homebrew is the headline; the shell
  installer is near-zero extra cost and serves non-brew users.
- **Tap: `MaximeDeconinck/homebrew-tap`** (generic name, reusable for future
  tools). cargo-dist commits `Formula/paddock.rb` into it automatically; it is
  never hand-edited.
- **Two repos.** `paddock` holds source + releases (artifacts live in its GitHub
  Releases); `homebrew-tap` holds only the generated formula (a pointer). This
  is the conventional split.
- **homebrew-core deferred.** `brew install paddock` (bare, no tap) is a later
  goal gated on notability, matching llmfit's trajectory.
- **First tag: `v0.1.0`** (version stays 0.1.0).

## Components

### 1. Repository metadata (`Cargo.toml`)

cargo-dist requires a `repository` URL to know where releases live. Add to
`[workspace.package]`:

```toml
repository = "https://github.com/MaximeDeconinck/paddock"
```

Both crates inherit workspace metadata, so this covers the workspace. The
`paddock` bin crate is the only distributed artifact; `paddock-core` is a
library and is not published as a binary (cargo-dist packages binaries, so it is
naturally excluded).

### 2. cargo-dist config (`dist-workspace.toml`)

`dist init` writes the config (recent `dist` uses `dist-workspace.toml` at the
workspace root; if the installed version writes `[workspace.metadata.dist]` in
`Cargo.toml` instead, that is equally acceptable - the location is the tool's
choice, not a requirement of this spec). The config must express:

- `targets = ["aarch64-apple-darwin"]`
- `installers = ["homebrew", "shell"]`
- `tap = "MaximeDeconinck/homebrew-tap"`
- the CI backend is GitHub Actions

The pinned `dist` version cargo-dist records in the config is whatever the
locally installed `dist` is; keep it consistent between local runs and CI (the
generated workflow pins it).

### 3. Release workflow (`.github/workflows/release.yml`)

Generated by `dist generate` (or written by `dist init`). Triggered on tags
matching the release pattern (`v*` / `paddock-v*` depending on the tool's
convention). Jobs: plan → build `aarch64-apple-darwin` → upload artifacts →
create the GitHub Release → publish the Homebrew formula to the tap and host the
`install.sh`. Do not hand-edit the generated workflow beyond what `dist`
supports via config (regenerating overwrites it).

### 4. Tap repo (user action, outside this repo)

`MaximeDeconinck/homebrew-tap`, created empty and public. cargo-dist's Homebrew
publish step commits `Formula/paddock.rb` into it on each release. The workflow
needs write access to a second repo, which the default `GITHUB_TOKEN` cannot
provide, so a Personal Access Token (scope: write/contents on the tap) is stored
as a secret in the `paddock` repo. The exact secret name follows cargo-dist's
convention (commonly a custom PAT wired via the config's `github-token` /
`tap` publish settings); confirm and document the name `dist init` expects.

### 5. README Install section

Replace the current `cargo install --path` block and the "A Homebrew formula is
coming" line with:

- `brew install maximedeconinck/tap/paddock` (primary)
- the `curl … | sh` one-liner (secondary)
- keep `cargo install` as the from-source fallback
- keep the "macOS on Apple Silicon (M1 or later)" requirement note

Use `-` or ` · ` as separators; the em-dash `—` is banned project-wide.

## Error handling / risks

- **macOS GUI deps** (`tray-icon`, `tao`, `arboard`): built for the native
  `aarch64-apple-darwin` target, so no cross-compilation. Validated by a local
  `dist build` before the first tag. If the build fails, resolve before tagging
  (do not push a tag that triggers a broken release).
- **Token missing/insufficient**: the Homebrew publish step fails while the
  GitHub Release still succeeds. Mitigation: confirm the PAT secret exists before
  the first tag; a dry `dist plan` surfaces config problems without publishing.
- **Regeneration drift**: hand-edits to `release.yml` are lost on the next
  `dist generate`. Mitigation: keep all changes in the dist config, never in the
  workflow.

## Verification

Packaging has no meaningfully unit-testable logic, so verification is
tool-driven, not TDD:

- `dist plan` succeeds and shows a single `aarch64-apple-darwin` artifact plus
  the homebrew + shell installers.
- `dist build` locally produces the arm64 binary archive and a generated
  `paddock.rb` formula referencing the correct artifact URL and a `sha256`.
- The generated `release.yml` exists and targets only `aarch64-apple-darwin`.
- README renders the new install commands; no em-dash present.
- End-to-end (after merge, user-triggered): push `v0.1.0`, confirm the CI is
  green, the GitHub Release has the artifacts, the tap gets `Formula/paddock.rb`,
  and `brew install maximedeconinck/tap/paddock` installs a working binary.

Because the real end-to-end proof requires a tag + the user-owned tap/token, the
in-repo work (config, workflow, README) is executed and verified locally with
`dist plan`/`dist build`; the tag push and live install check are user actions
after merge.

## Execution note

This is configuration + CI + docs with no unit-testable units, so it is executed
inline (not via the subagent-driven TDD flow, which is a poor fit here).

## Out of scope (YAGNI)

- Intel (`x86_64-apple-darwin`) and Linux targets.
- homebrew-core submission.
- Code signing / notarization (CLI binaries via brew/curl install without it;
  revisit only if Gatekeeper blocks users).
- Bottles for multiple macOS versions beyond what a single arm64 build covers.
- npm / other installer backends cargo-dist supports.
